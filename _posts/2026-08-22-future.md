The technical question I am interested in is:

**Can observable human behavior be converted into a representation that another physical embodiment can execute?**

A simplified pipeline is:

```text
RGB video
→ human + scene reconstruction
→ world-space motion
→ contacts + task constraints
→ embodiment-independent representation
→ robot retargeting
→ physics-valid reference motion
→ whole-body controller
→ simulation
→ sim-to-real
→ physical humanoid
```

At first this can look like pose estimation followed by animation.

It is not.

The difficult part is that **pixels are measurements, not physical state**.

A monocular RGB video does not explicitly give us depth, metric scale, force, torque, contact state, object mass, friction, intent or hidden geometry.

Almost everything downstream has to be estimated, inferred or learned.

## 1. Start With Pixels

A normal video is a sequence:

[
I_1, I_2, \ldots, I_T
]

where each frame can be represented as:

[
I_t \in \mathbb{R}^{H \times W \times 3}
]

For a human observer, the transformation happens almost automatically:

```text
pixels → "person picks up box"
```

For a robot-learning system, we need something closer to:

```text
pixels
→ person tracks
→ camera trajectory
→ 3D body
→ 3D scene
→ object tracks
→ contacts
→ task
→ physical constraints
→ control
```

That difference is the core problem.

## 2. Recover the Human in 3D

The first useful intermediate representation is an articulated human body.

Instead of storing independent coordinates for every image pixel, a parametric human model can represent the person using compact pose and shape parameters.

Conceptually, at timestep `t`:

```python
human_t = {
    "root_position": [x, y, z],
    "root_orientation": [qw, qx, qy, qz],
    "joint_rotations": [...],
    "body_shape": beta,
}
```

This already gives us something much more useful than raw RGB.

But there is another major issue: **camera motion**.

A person walking forward while the camera stays still can look similar in image space to a stationary person while the camera moves backward.

So we need to recover both:

```text
human motion
+
camera motion
```

and place the reconstructed motion into a stable world coordinate system.

Without that, the robot may learn completely wrong trajectories.

## 3. Go Beyond a Skeleton

A 3D skeleton alone is probably too weak for Physical AI.

A more useful representation might combine geometry, kinematics, contacts, semantics and style.

For example:

```python
motion_state = {
    "root_pose": ...,
    "joint_pose": ...,
    "joint_velocity": ...,
    "left_hand_pose": ...,
    "right_hand_pose": ...,
    "left_foot_contact": True,
    "right_foot_contact": False,
    "object_states": ...,
    "active_contacts": ...,
    "task_phase": ...,
    "task": ...,
    "style_embedding": ...
}
```

I would separate the representation into several layers:

**Geometry:** where things are.
**Kinematics:** how they move.
**Dynamics:** why the motion is physically possible.
**Contact:** which bodies interact.
**Task semantics:** what result is being attempted.
**Style:** how an individual tends to execute the behavior.

These should not be treated as the same thing.

## 4. Why 3D Pose Is Not Enough

Imagine a video of a hand pushing a heavy door.

We may reconstruct the hand, elbow and door trajectory accurately.

But that does not tell us the required force.

The same visible trajectory could come from:

```text
door mass = 1 kg
```

or:

```text
door mass = 50 kg
```

The images alone do not uniquely determine the underlying physics.

Video-to-robot learning is therefore partly an inverse problem.

We observe the result and try to infer the hidden physical state that produced it.

Additional information can help constrain this, including repeated demonstrations, robot interaction, force sensors, known object models, scene priors or learned world models.

## 5. Human Skeleton != Robot Skeleton

Even if human reconstruction were perfect, this would not work:

```python
robot_joint_angles = human_joint_angles
```

A humanoid robot has different link lengths, joint limits, masses, actuator characteristics and available degrees of freedom.

So we need **motion retargeting**.

Suppose the human provides important task-space targets:

[
p_i^H(t)
]

for points such as the pelvis, hands, feet and head.

The robot has generalized coordinates:

[
q_t
]

and forward kinematics:

[
f_i(q_t)
]

A simplified retargeting objective might be:

[
q_t^* =
\arg\min_q
\sum_i w_i
\left|
f_i(q)-p_i^H(t)
\right|^2
+
\lambda_s
\left|
q-q_{t-1}
\right|^2
+
P(q)
]

where the first term follows important human targets, the second encourages temporal smoothness and `P(q)` can include penalties for joint-limit violations, self-collision or other constraints.

In simplified code:

```python
def retarget(human, robot):
    targets = {
        "pelvis": human.pelvis,
        "left_hand": human.left_hand,
        "right_hand": human.right_hand,
        "left_foot": human.left_foot,
        "right_foot": human.right_foot,
    }

    return solve_inverse_kinematics(
        robot=robot,
        targets=targets,
        joint_limits=True,
        collision_constraints=True,
        smoothness=True,
    )
```

But an inverse-kinematics solution can still fall immediately when physics is enabled.

## 6. Kinematic Validity vs Dynamic Validity

This distinction is critical.

A motion can be **kinematically valid** and still be **dynamically impossible**.

The simulator may place the robot's foot exactly where we request, but the robot may not be able to generate the required torque while keeping itself balanced.

So after retargeting, we have to care about:

**joint position limits, velocity limits, torque limits, self-collision, centre of mass, ground reaction forces, friction, contact timing, momentum and actuator dynamics.**

This is where animation becomes robotics.

## 7. Contacts Matter

Walking is a simple example.

Pose reconstruction gives us:

```text
left_ankle_position(t)
```

But the controller also needs to know:

```text
left_foot_contact(t) ∈ {0, 1}
```

When the foot is planted, its velocity relative to the ground should be approximately zero:

[
v_{\text{foot}} \approx 0
]

Without contact reasoning, reconstructed motion often produces foot sliding.

A contact-aware representation could look like:

```python
contact = {
    "left_foot": 1,
    "right_foot": 0,
    "left_hand": 0,
    "right_hand": 1,
}
```

This becomes even more important for sitting, climbing stairs, lifting, pushing, opening doors and tool use.

Once objects enter the scene, human pose alone is no longer enough.

We need human-object interaction.

## 8. Reference Motion Is Not the Controller

After retargeting, suppose we have a reference trajectory:

```text
q_ref(t)
```

That still does not make the robot execute it.

A basic controller may use PD control:

[
\tau =
K_p(q_{ref}-q)
+
K_d(\dot{q}_{ref}-\dot{q})
]

For more complex humanoid behavior, we may instead train a whole-body policy.

The observation might include:

```python
observation = {
    "joint_positions": q,
    "joint_velocities": dq,
    "imu": imu,
    "root_velocity": root_velocity,
    "contacts": contacts,
    "reference_motion": reference[t],
}
```

The policy produces:

```python
action = policy(observation)
```

The action could represent target joint positions, velocities, torques or residual corrections.

The control loop becomes:

```python
for t in range(T):
    state = robot.observe()
    target = reference[t]

    action = controller(
        state=state,
        target=target,
    )

    robot.step(action)
```

This is very different from replaying an animation.

The controller is continuously correcting errors created by physics.

## 9. An Embodiment-Independent Layer

The representation I find most interesting is not:

```text
human → exact robot commands
```

but:

```text
human
→ abstract physical behavior
→ embodiment-specific controller
→ robot
```

This would make human motion more portable.

Instead of preserving exact joint trajectories, we try to preserve the important task constraints and behavior.

That could include:

```text
desired hand trajectory
desired foot contacts
relative object pose
body orientation
centre-of-mass behavior
motion rhythm
task phase
style
```

Then different embodiments solve the task using their own mechanics.

## 10. Separate Motion Content From Style

I also want to think about motion as something like:

[
M = f(C, S, E)
]

where:

`C = motion content`
`S = individual style`
`E = embodiment`

For example:

```text
C = walk forward five meters
```

while style may contain:

```text
cadence
posture
arm swing
stride characteristics
torso movement
acceleration profile
```

and embodiment could be:

```text
human
Unitree G1
another humanoid
virtual avatar
```

The goal becomes:

[
M_{\text{robot}} = f(C,S,E_{\text{robot}})
]

rather than trying to copy the original human motion joint by joint.

That would let us ask a much more interesting question:

**Can a short set of examples capture something about a person's movement style and apply it to an unseen task?**

If the system only reproduces recorded clips, we built a motion library.

If the style generalizes, we may have learned a reusable representation.

## 11. Simulation

Simulation is where I would test all of this before touching real hardware.

A minimal pipeline could look like:

```python
video = load_video("human.mp4")

human_motion = reconstruct_human(video)

world_motion = recover_world_coordinates(
    human_motion
)

contacts = estimate_contacts(
    video,
    world_motion
)

robot_reference = retarget(
    human_motion=world_motion,
    contacts=contacts,
    robot="unitree_g1",
)

simulate(robot_reference)
```

The important metrics are not whether the motion looks visually impressive.

I would measure:

**3D reconstruction error, root trajectory error, end-effector tracking error, foot sliding, contact accuracy, joint-limit violations, torque-limit violations, energy consumption, fall rate and motion completion rate.**

Then intentionally make the simulator worse.

For example:

```text
friction ±20%
robot mass ±10%
motor strength ±10%
sensor noise
latency
ground stiffness
```

If the controller completely fails after small physical changes, it probably has not learned a robust behavior.

## 12. The Reality Gap

Simulation is still not reality.

A real robot contains effects that the simulator does not perfectly capture: motor latency, gearbox friction, backlash, sensor noise, structural compliance, battery variation, temperature changes, floor variation and unexpected contacts.

This is the **sim-to-real gap**.

Several strategies can help:

```text
domain randomization
system identification
actuator modeling
residual learning
real-world fine-tuning
online adaptation
```

One useful idea is to learn a correction between simulated and real behavior.

Conceptually:

```text
simulated dynamics
+
learned real-world correction
→ improved model
→ improved policy
```

This feedback loop matters because physical intelligence will probably not be learned only from internet data.

Eventually the real world has to become part of the training system.

## 13. What Video Still Cannot Give Us

This is where the problem becomes larger than motion imitation.

A video of an expert may tell us what their hands did.

It may not reveal what they noticed, what force they felt, what alternative they rejected, why they changed strategy or which memory they used.

A more complete physical-skill representation might eventually combine:

**vision, audio, language, proprioception, force, touch, eye gaze, environment state and task outcome.**

Possibly one day neural signals become another source.

Video may still be the most scalable starting point because humanity has already produced an enormous amount of it.

But video alone is probably not the full answer.

## 14. Neural Interfaces Are Another Input, Not a Brain Copy

Brain-computer interfaces are conceptually interesting here, but current systems should not be confused with mind uploading.

The current pipeline is closer to:

```text
neural activity
→ signal decoding
→ movement intention
→ external device command
```

not:

```text
brain
→ complete human software
```

In the future, neural information could potentially complement externally observable signals such as speech, movement, actions, memories and preferences.

Whether anything resembling a copied human mind becomes possible is a separate scientific problem.

## 15. The Embodiment Problem

Even as a thought experiment, suppose we somehow produced a perfect computational representation of a person's brain.

We would still have the embodiment problem.

A biological nervous system learned inside human muscles, bones, skin, eyes, hands and a vestibular system.

Now give that intelligence:

```text
robot joints
electric motors
cameras
depth sensors
metal feet
different body proportions
different latency
```

How does it move?

There is no obvious mapping.

Even a perfect digital mind would still need an adaptation layer between:

```text
"I want to reach for the cup"
```

and:

```text
τ1, τ2, τ3, ... τn
```

for a completely different body.

This may be the deeper robotics problem:

**embodied intelligence is not simply intelligence plus a robot body.**

The intelligence and the body must learn how to operate together.

## 16. The Prototype I Would Build

Rather than beginning with "digital humans," I would break the problem into small stages.

### Stage 1: Video → world-space human

Input:

```text
ordinary monocular MP4
```

Output:

```text
3D body
global root trajectory
camera trajectory
```

### Stage 2: Human → robot kinematics

Retarget important points:

```text
pelvis
hands
feet
head
torso
```

Measure:

```text
retargeting error
joint-limit violations
temporal jitter
```

### Stage 3: Contact-aware retargeting

Estimate:

```text
foot-ground contacts
hand-object contacts
```

Measure:

```text
foot sliding
contact consistency
```

### Stage 4: Physics

Run the reference inside MuJoCo, Isaac Sim or another dynamics engine.

Add:

```text
mass
gravity
friction
actuator limits
collisions
```

Measure:

```text
falls
torque saturation
centre-of-mass stability
tracking error
```

### Stage 5: Learned tracking controller

Train a policy:

[
\pi(a_t|s_t,r_t)
]

where:

`s_t = current robot state`
`r_t = target reference`
`a_t = control action`

### Stage 6: Robustness

Randomize:

```text
mass
friction
latency
motor strength
sensor noise
```

### Stage 7: Style

Collect multiple clips from the same person.

Learn:

```text
style_encoder(motion) → z_style
```

Then test:

```python
new_motion = generator(
    content="walk_and_turn",
    style=z_style_person_A,
    embodiment="g1",
)
```

The key experiment is generalization.

If the system only reproduces recorded clips, it is a motion database.

If a short sample captures something about the person's movement and applies it to unseen behaviors, we may have learned something reusable.

**video.**

## 18. Why This Matters

Humanity has stored enormous amounts of knowledge in books, documents, audio and video.

LLMs made text computationally useful in a completely new way.

Something similar may eventually happen to physical behavior.

A technician with thirty years of experience does not only possess sentences that can become tokens.

They possess **perceptual habits, motor patterns, timing, physical heuristics, failure recovery and interaction strategies.**

Today much of that information disappears.

If some of it can be transformed into structured physical representations, it could become useful for robot learning, industrial training, simulation, digital twins, teleoperation, assistive robotics and skill preservation.

That does not mean we have copied the human.

It means we captured another category of information that previously existed mainly inside biological experience.

## Conclusion

The interesting problem for me is no longer simply:

```text
video → pose
```

It is:

```text
pixels
→ geometry
→ motion
→ contact
→ intent
→ task
→ style
→ physical constraints
→ embodiment
→ control
→ reality
```

The early parts of this pipeline are becoming increasingly practical.

The later parts remain extremely difficult.

That is exactly why I find the problem interesting.

Maybe human physical knowledge eventually becomes portable between humans, simulations, avatars and machines. Maybe brain interfaces create another path. Maybe entirely new representations replace what we use today.

For now, the experiment can remain much smaller:

```text
one video
→ one human motion
→ one structured representation
→ one simulated humanoid
→ one physically valid behavior
```

Then find the next failure.

Fix it.

And repeat.
